# Plan: Implement Regulatory Compliance Logging (Phase 2.1)

## Overview
Implement comprehensive audit trails for all trading activities, balance changes, and system events to meet regulatory compliance requirements. This includes database-backed audit logs with timestamps, metadata, and export functionality.

## Current State Analysis
- Existing logging is file-based JSON logs via `backend/logging/logger.ts`
- Trade data stored in `shadow_trades` table with basic fields
- Balance changes managed in `balances` table without audit history
- No audit trails for API actions or system events
- Dependencies: PostgreSQL migration complete, database indexes added

## Implementation Plan

### Day 1: Database Schema Design & Migration (1 day)
**Objective:** Create audit tables and update schema.

**Tasks:**
1. Design audit tables:
   - `audit_trades`: Log all trade lifecycle events (open, close, partial exits)
   - `audit_balances`: Log all balance changes with reasons
   - `audit_user_actions`: Log API requests (especially mutating operations)
   - `audit_system_events`: Log system events (circuit breakers, regime changes, errors)

2. Add schema to `database_postgres.ts` init function

3. Create migration script to add tables to existing databases

4. Add indexes for performance on timestamp and entity ID fields

**Success Criteria:**
- All audit tables created with proper constraints
- Indexes added for query performance
- Migration script tested on both SQLite and PostgreSQL

### Day 2: Trade Audit Logging (1 day)
**Objective:** Log all trade-related activities in ShadowTrader.

**Tasks:**
1. Modify `ShadowTrader.processSignal()` to log trade open events
2. Update `updatePositions()` to log trade close/partial exit events
3. Add metadata: risk mode, leverage, exit reason, PnL, etc.
4. Ensure logs include timestamps and unique event IDs

**Files to Modify:**
- `backend/shadow/shadow_trader.ts`

**Success Criteria:**
- Every trade open logged with full metadata
- Every trade close/partial exit logged with PnL and reason
- Logs stored in `audit_trades` table

### Day 3: Balance Audit Logging (1 day)
**Objective:** Track all balance changes with audit trail.

**Tasks:**
1. Modify `BalanceManager` methods to log changes:
   - `allocateToBot()`: Log allocation reason
   - `withdrawFromBot()`: Log withdrawal reason
   - `recordTradeResult()`: Log PnL adjustments
   - `addActiveTrade()`: Log trade value movements
2. Include before/after balances and change reasons

**Files to Modify:**
- `backend/balance/manager.ts`

**Success Criteria:**
- All balance changes logged with timestamps and metadata
- Reconciliation possible via audit trail

### Day 4: User Actions & System Events Audit (1 day)
**Objective:** Log user API actions and system events.

**Tasks:**
1. Create audit middleware for API routes to log mutating requests:
   - User role, IP address, endpoint, request body (sanitized), timestamp
   - Log to `audit_user_actions` table

2. Add system event logging:
   - Circuit breaker activations in `RiskManager`
   - Regime changes in `RegimeDetector`
   - Critical errors and system state changes
   - Log to `audit_system_events` table

3. Implement export endpoint for regulatory reporting:
   - GET /api/audit/export with date range and type filters
   - Export in CSV/JSON format
   - Require admin role

4. Add balance reconciliation report endpoint:
   - GET /api/reports/balance-reconciliation
   - Generate report comparing current balances with audit trail

**Files to Modify:**
- `backend/api/routes.ts` (add middleware and endpoints)
- `backend/risk/manager.ts` (circuit breaker events)
- `backend/regime/detector.ts` (regime changes)

**Success Criteria:**
- All trading API actions logged
- System events logged (circuit breakers, regime changes)
- Export functionality for CSV/JSON audit reports
- Balance reconciliation reports available

## Testing & Validation
- Unit tests for audit logging functions
- Integration tests verifying logs are written on trade/balance operations
- Test export endpoints return correct data
- Validate audit data integrity (no missing logs, proper metadata)

## Security Considerations
- Sanitize sensitive data in audit logs (no API keys, secrets)
- Role-based access to audit exports (admin only)
- Rate limiting on export endpoints
- Audit logs should be tamper-evident (consider hashing or blockchain for high compliance)

- Day 1: Schema & Migration (4-6 hours)
- Day 2: Trade Logging (6-8 hours)
- Day 3: Balance Logging (6-8 hours)
- Day 4: User Actions & Exports (6-8 hours)

- ✅ All trades logged with timestamps and metadata
- ✅ Balance reconciliation reports

## Risk Mitigation
- Backward compatibility: Audit logging is additive, doesn't break existing functionality
- Performance: Use async logging, add indexes for queries
- Data retention: Consider log rotation/archiving policies (not in scope for this phase)

## Next Steps
After completion, integrate with monitoring dashboards and consider external audit storage for long-term retention.
