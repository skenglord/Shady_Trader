## Executive Summary

This execution roadmap provides a rigorous technical decomposition for implementing a production-ready Monte Carlo Simulation Engine for the Shady_Trader platform. The engine performs probabilistic risk assessment across 6 shadow trading portfolios, generating Value-at-Risk (VaR), Conditional VaR (CVaR), and portfolio stress scenarios with sub-100ms latency requirements.

**Key Objectives:**
- Generate 100,000+ correlated price paths in <1s (CPU) or <100ms (GPU)
- Compute VaR/CVaR at 95% and 99% confidence levels with Kupiec backtesting
- Maintain positive semi-definite correlation matrices under stress scenarios
- Achieve zero look-ahead bias and full reproducibility via deterministic seeding

**Technical Stack:**
- **NumJS**: N-dimensional arrays and linear algebra (NumPy-like API)
- **simple-statistics**: Statistical distributions and hypothesis tests  
- **ml-matrix**: Matrix operations for Cholesky decomposition
- **gpu.js**: GPU acceleration for path simulation (WebGL-based)
- **seedrandom**: Deterministic random number generation

**Integration Points:**
- ShadowTrader: VaR limits for position sizing
- RiskManager: Stress test results for circuit breakers
- RegimeDetector: Correlation matrices for regime classification
- OptimizationEngine: MC results for parameter tuning

  - API: `partition(series, in_sample_ratio=0.7, step_size=1, mode='anchored'|'non-anchored')`

**Day 2: Rolling Optimization Engine** ✅ COMPLETED

**Day 3: Overfitting Detection Module** ✅ COMPLETED
- Implemented divergence metrics between in-sample (IS) and out-of-sample (OOS) equity curves:
  - **Divergence Ratio**: `|μ_IS - μ_OOS| / σ_IS` (threshold: >0.3 flags overfitting)
  - **Correlation Decay**: Rolling correlation between IS/OOS returns (window=20, threshold: <0.4)
  - **Shape Test**: Kolmogorov-Smirnov test on return distributions (p<0.05 rejects stability)
  - **Complexity Penalty**: Schwartz Information Criterion (SIC) for parameter count
- Created comprehensive stability analysis across folds
- Implemented Kolmogorov-Smirnov test for distribution equality
- Added recommendation engine for overfitting mitigation
- Created visualization utilities for equity curves and diagnostics
- **Location**: `backend/validation/wfa/overfitting-detector.ts`, `backend/validation/wfa/validation-visualizer.ts`

**Day 4: Statistical Validation Layer** ✅ COMPLETED

### 1.3 Data Integrity & Risk Mitigation

**Look-Ahead Bias Prevention:**
- Strict temporal partitioning: All indicator calculations use `.shift(1)` to prevent forward leakage
- Indicator warmup: 50-candle minimum before first optimization (enforced via assertion)
- Timezone-aware indexing: UTC timestamps with monotonicity checks
- Immutable data views: Object.freeze() for partition arrays to prevent mutation

**Survivorship Bias Mitigation:**
- Use delisted/historical data where available (CoinMarketCap delisting API)
- Implement `SurvivorshipAdjuster`: Bootstrap sampling with replacement from historical constituents
- Flag assets with <6 months history as high-bias (exclude from WFA)

**Data Leakage Controls:**
- Hash verification: SHA-256 checksum of input data per partition
- Cross-validation guard: Ensure no overlap between IS/OOS sets (assert `is_end <= os_start`)
- Type-safe data contracts with Zod schemas for all partition inputs

**Overfitting Safeguards:**
- Parameter count limit: Max 5 free parameters per mode (enforced via L1 regularization)
- Out-of-sample minimum: Require ≥30 OOS observations per fold
- Stability test: Coefficient of variation of IS Sharpe across folds < 0.25
- Early stopping: Halt optimization if OOS performance degrades for 5 consecutive iterations

## Module 2: Monte Carlo Simulation Engine

### 2.1 Technical Architecture & Stack

**Core Stack:**
- **NumJS**: N-dimensional arrays and linear algebra (NumPy-like API for JavaScript)
- **simple-statistics**: Statistical distributions and hypothesis tests
- **ml-matrix**: Matrix operations for Cholesky decomposition
- **gpu.js**: GPU acceleration for path simulation (WebGL-based, runs in Node.js)
- **seedrandom**: Deterministic random number generation for reproducibility

**Rationale:** NumJS provides vectorized operations without Python dependency. ml-matrix offers optimized linear algebra. gpu.js enables GPU acceleration using WebGL (works in Node.js via headless-gl). Simple-statistics provides comprehensive statistical functions. All dependencies are pure JavaScript/TypeScript, ensuring cross-platform compatibility.

### 2.2 Granular Execution Roadmap (Days 6-10)

**Day 6: Stochastic Path Generation**
- Implement Geometric Brownian Motion (GBM) base model:
  - `dS = μS·dt + σS·dW` where `dW ~ N(0, dt)`
  - Vectorized: `S_t = S_0 * exp((μ - σ²/2)t + σW_t)`
- Add Jump Diffusion extension (Merton model):
  - Jump intensity λ (Poisson process)
  - Jump size ~ N(μ_j, σ_j²)
  - Calibrate λ, μ_j, σ_j from historical tail events (3σ+ moves)
- Support for stochastic volatility (Heston model placeholder)

**Day 7: Correlation & Cholesky Decomposition**
- Build `CorrelationMatrix` class:
  - Input: Historical returns (6 modes × 100+ assets)
  - Method: Ledoit-Wolf shrinkage for covariance estimation
  - Decomposition: Cholesky (LL^T) via ml-matrix (GPU fallback)
  - Validation: Positive definiteness check (min eigenvalue > 1e-8)
- Implement correlation stress scenarios:
  - Crisis mode: Off-diagonals × 1.5 (correlation breakdown)
  - Flight-to-quality: All correlations → 1.0

**Day 8: VaR & CVaR Implementation**
- **Parametric VaR** (variance-covariance):
  - `VaR_α = μ - z_ασ` for normal returns
  - Cornish-Fisher expansion for skewness/kurtosis adjustment
- **Historical VaR**: Empirical quantile from simulated paths
- **Conditional VaR (CVaR/Expected Shortfall)**:
  - `CVaR_α = E[L | L > VaR_α]`
  - Implement via tail expectation (average of worst 1-α losses)
- **Component VaR**: Marginal contribution per mode/asset (Euler allocation)

**Day 9: Portfolio Stress Testing**
- Implement scenario library:
  - **Black Swan**: 6σ event across all assets
  - **Flash Crash**: -10% in 5 minutes (2010-style)
  - **Liquidity Crisis**: Bid-ask spread × 10, volume ↓ 90%
  - **Regime Shift**: Correlation matrix replacement (bull→bear)
- Run 100k simulations per scenario (parallel via NumJS prange)
- Generate risk reports: VaR/CVaR heatmaps, tail dependency plots

**Day 10: Integration & Performance Optimization**
- Expose Monte Carlo results via API: `POST /api/mc/simulate` (async job via BullMQ)
- WebSocket streaming: Progress updates (0-100%) and partial results
- GPU acceleration: Auto-detect WebGL, fallback to CPU with AVX2
- Benchmark: 10k paths × 252 steps in <500ms (CPU), <50ms (GPU)
- Unit tests: Distribution accuracy, correlation preservation, VaR calibration

### 2.3 Data Integrity & Risk Mitigation

**Non-Normality Handling:**
- Use multivariate t-distribution (ν=5 degrees of freedom) for fat tails
- Cornish-Fisher adjustment for skewness in VaR calculation
- Backtest VaR violations (Kupiec test) – reject model if violation rate > α+2√(α(1-α)/n)

**Correlation Breakdown:**
- Stress test with correlation → 1.0 (worst-case diversification failure)
- Implement dynamic correlation: DCC-GARCH model for time-varying dependencies
- Flag assets with correlation instability (rolling window std > 0.3)

**Simulation Risk:**
- Seed control: Deterministic seeds for reproducibility (PCG64DXSM with mode-specific seeds)
- Path validation: Ensure no negative prices (max(S_t, 1e-8))
- Convergence test: CVaR stable within 5% when doubling path count

**Model Risk:**
- Ensemble approach: Average VaR from GBM, Jump Diffusion, and Historical methods
- Model confidence bounds: Report VaR as range [min, max] across models
- Backtesting: Compare simulated P&L distribution to actual P&L (QQ-plot)

### 2.4 Definition of Done (DoD)

- [ ] 100k paths simulated in <1s (CPU) or <100ms (GPU)
- [ ] VaR backtesting passes Kupiec test (p>0.05) for all modes
- [ ] CVaR reported with 95% and 99% confidence levels
- [ ] Correlation matrix positive definite for all stress scenarios
- [ ] API handles 100 concurrent simulation requests (load test)

## Module 3: Transaction Cost & Slippage Modeling

### 3.1 Technical Architecture & Stack

**Core Stack:**
- **NumJS**: Vectorized cost calculations across large trade arrays
- **ccxt**: Exchange-specific fee structures (real-time via API)
- **decimal.js**: Arbitrary-precision decimal arithmetic for financial calculations
- **ml-regression**: Polynomial regression for liquidity impact model calibration

**Rationale:** NumJS provides vectorized operations for performance. ccxt is already used in the codebase for exchange connectivity. decimal.js prevents floating-point errors in financial calculations. ml-regression enables efficient calibration of slippage models from historical data. All components are TypeScript-compatible.

### 3.2 Granular Execution Roadmap (Days 11-14)

**Day 11: Cost-Overlay Architecture**
- Design `TransactionCostModel` base class with pluggable strategies:
  - `FixedFeeModel`: Maker/taker fees from exchange API
  - `SlippageModel`: Market impact + spread costs
  - `NetworkCostModel`: Blockchain gas fees (for on-chain settlement)
- Implement cost aggregation: `TotalCost = Σ(Fee_i + Slippage_i + Network_i)`
- Cache fee schedules: Refresh every 6 hours (or on API error)

**Day 12: Stochastic Slippage Models**
- **Spread Slippage**: 
  - `S = 0.5 × (Ask - Bid) × TradeDirection`
  - Model spread as stochastic process: `dSpread = κ(μ - Spread)dt + σdW` (mean-reverting)
- **Market Impact** (permanent + temporary):
  - Permanent: `ΔP_perm = γ × TradeSize / ADV` (square-root law)
  - Temporary: `ΔP_temp = λ × TradeSize / Volume` (exponential decay)
  - Calibrate γ, λ from historical trade data (VWAP slippage analysis)
- **Implementation Shortfall**: 
  - Simulate execution delay (10ms-100ms) with price drift
  - `Cost = |P_execution - P_decision| × Quantity`

**Day 13: Exchange-Specific Adaptors**
- Build `ExchangeFeeAdapter` for each exchange (Binance, Kraken, OKX, Coinbase)
  - Fetch maker/taker fees via REST (authenticated)
  - Handle VIP tiers and volume-based discounts
  - WebSocket for real-time fee updates (if available)
- Implement liquidity tiers:
  - Tier 1 (high volume): 0.1% slippage model
  - Tier 2 (medium): 0.25% slippage
  - Tier 3 (low): 0.5% + volatility penalty

**Day 14: Integration with Trading Engine**
- Modify `ShadowTrader` to accept cost-adjusted signals:
  - `Signal_Adjusted = Signal_Raw - Cost_Expected`
  - Reject trades if Cost > Threshold (configurable per mode)
- Implement pre-trade cost check: `estimate_cost(order)` → `bool`
- Post-trade analysis: Compare estimated vs. actual slippage (feedback loop)
- Unit tests: Cost accuracy within 10% of historical slippage

### 3.3 Data Integrity & Risk Mitigation

**Fee Arbitrage Prevention:**
- Lock fee schedule at order creation (prevent mid-trade changes)
- Versioned fee cache: Hash of fee data included in order signature
- Alert on fee changes > 50% during trading session

**Slippage Model Risk:**
- Calibrate models daily using realized slippage (exponential weighting λ=0.9)
- Upper bound: Cap slippage estimate at 5% (prevent infinite loss scenarios)
- Stress test: 10x normal volume → 5x slippage multiplier

**Data Freshness:**
- Fee cache TTL: 6 hours (or 1 hour during high volatility)
- Stale data detection: Compare cached vs. live fees (alert if > 10% diff)
- Fallback: Use conservative estimates if API unavailable

**Exchange-Specific Risks:**
- Handle fee schedule changes mid-session (WebSocket disconnects)
- Implement circuit breaker: Pause trading if fee data unavailable > 5 minutes
- Cross-validate: Compare ccxt fees with exchange documentation

### 3.4 Definition of Done (DoD)

- [ ] Cost estimates within 10% of actual slippage (backtest on 1000 trades)
- [ ] All 5 exchanges supported with live fee fetching
- [ ] Pre-trade cost check latency < 1ms (p95)
- [ ] Slippage model adapts to volatility (correlation > 0.3 with realized spread)
- [ ] Integration tests pass with ShadowTrader (cost-adjusted P&L accurate)

## Module 4: Live Paper Trading Environment

### 4.1 Technical Architecture & Stack

**Core Stack:**
- **Fastify**: High-performance REST API with async/await (lower overhead than FastAPI)
- **ws**: WebSocket library for real-time position updates
- **ioredis**: Redis client for Pub/Sub state synchronization
- **pg**: PostgreSQL client for persistent paper trading state
- **state-machine**: Formal state management for order lifecycle

**Rationale:** Fastify provides better throughput and lower latency than Express for high-frequency trading APIs. ws is the standard WebSocket library for Node.js with excellent performance. ioredis supports Redis Pub/Sub and clustering. pg offers robust PostgreSQL integration. All components are battle-tested in production trading systems and integrate seamlessly with the existing TypeScript codebase.

### 4.2 Granular Execution Roadmap (Days 15-19)

**Day 15: State Machine Design**
- Define states: `IDLE`, `PENDING_ORDER`, `OPEN_POSITION`, `PENDING_CLOSE`, `CLOSED`, `ERROR`
- Define events: `CREATE_ORDER`, `FILL_ORDER`, `CANCEL_ORDER`, `UPDATE_PRICE`, `CLOSE_POSITION`
- Implement guards: Prevent invalid transitions (e.g., cannot close from IDLE)
- Integrate with existing `ShadowTrader` modes (6 parallel state machines)

**Day 16: REST/Sync API Implementation**
- **Order Management**:
  - `POST /api/paper/order` (create limit/market order)
  - `PUT /api/paper/order/{id}/cancel` (cancel pending order)
  - `GET /api/paper/positions` (list open positions)
- **Price Synchronization**:
  - WebSocket endpoint: `ws://host/paper/stream`
  - Binary protocol: Protobuf messages for position updates (every 100ms)
  - Fallback: REST polling (every 1s) if WebSocket fails
- **State Persistence**:
  - Save all paper trades to PostgreSQL (mirror live trading schema)
  - Implement idempotency keys (prevent duplicate orders)

**Day 17: Real-Time Synchronization Logic**
- **Order Book Simulation**:
  - Maintain in-memory order book per symbol (top 10 levels)
  - Match paper orders against live market data (with slippage model)
  - Fill logic: Market orders fill at best bid/ask; limit orders queue
- **Position Tracking**:
  - Real-time P&L calculation: `P&L = (CurrentPrice - EntryPrice) × Quantity`
  - Unrealized P&L streamed via WebSocket (every price tick)
  - Risk checks: Validate against mode limits (max drawdown, position size)

**Day 18: Integration with Existing Systems**
- **Trading Engine Hook**:
  - Modify `TradingEngine` to route orders through paper environment when mode=paper
  - Preserve all existing logic (signals, risk checks) but replace live execution
  - Log divergence: Compare paper vs. hypothetical live execution
- **Dashboard Integration**:
  - Extend React UI with paper trading toggle
  - Real-time position cards (WebSocket-driven)
  - Historical paper P&L chart (vs. live modes)

**Day 19: Testing & Performance Optimization**
- **Load Testing**: Simulate 1000 concurrent paper traders (Locust)
- **Latency Optimization**: 
  - Redis pipelining for batch updates
  - WebSocket compression (permessage-deflate)
  - Target: Order-to-fill latency < 50ms (p95)
- **Chaos Engineering**: 
  - Simulate Redis failure (fallback to PostgreSQL polling)
  - Network partition test (recovery without data loss)
- **Final Integration**: End-to-end test with all 6 shadow modes

### 4.3 Data Integrity & Risk Mitigation

**State Consistency:**
- Distributed lock (Redis Redlock) for concurrent order modifications
- Idempotency: All mutating operations require unique idempotency key
- Event sourcing: Log all state transitions (audit trail)

**Synchronization Failures:**
- Heartbeat mechanism: Detect stale connections (30s timeout)
- Reconciliation job: Compare paper state vs. market data (hourly)
- Divergence alert: Flag if paper P&L deviates > 1% from expected

**Data Loss Prevention:**
- Write-ahead log: Persist orders before acknowledgment
- Replication: PostgreSQL streaming replication (1 replica)
- Backup: Daily snapshots of paper trading state

**Security:**
- Isolate paper balances from live funds (separate database schema)
- Rate limiting: 100 orders/minute per paper trader
- Validation: Reject paper orders exceeding mode limits (even in simulation)

- [ ] 1000 concurrent paper traders supported (load test passes)

- [ ] Zero state inconsistencies in 24-hour stress test
